# 12 工程架构

## 1. 产品分层

IF 的核心交付物是垂直领域 agent harness；Tauri 叙事应用是首个宿主和验收入口。核心层应能在没有 React UI 的情况下运行回合、执行工具、调用 Judge、提交事件并重放结果。宿主层可以替换为桌面 UI、测试 runner 或未来的服务端接口。

```text
IF harness（可复用核心）
  runtime / tools / views / judge / policy / event commit / replay
          │
反事实叙事领域插件
  world model / IF rules / story tasks / lore adapter / tavern mapping
          │
首个宿主应用
  Tauri + React：酒馆式游戏 / 沙盒 UI
```

## 2. 技术栈

- 桌面外壳：Tauri 2
- 界面：React + TypeScript（在 `frontend-example/` 的基础上开发）
- 核心：Rust
- LLM 层：基于 Onemore 改造（见 [05](05-Agent运行时.md)）

## 3. crate 分层

```
React UI ──(Tauri invoke / emit)── if-app
                                     │
                              if-pipeline（回合编排、任务 host、兜底）
                ┌──────────┬─────────┼──────────┬───────────┐
            if-agent   if-judge   if-views   if-policy   if-lore
        （Onemore 核心）（Judge 接口）（视图编译）（裁决、骰子）（世界书、导入）
                └──────────┴─────────┼──────────┴───────────┘
                                 if-domain（领域类型）
                                     │
                                 if-store（SQLite 事件存储、投影、世界线）
```

| crate | 职责 |
|---|---|
| `if-domain` | 领域类型：Subject、Proposition、Fact、Belief、Claim、WorldRule、Thread、Tendency、LoreEntry、Scene、Event、TurnRecord 等 |
| `if-store` | 会话事件日志、投影与快照、世界线；应用级**世界库**（世界资产、来源、设定条目） |
| `if-agent` | 从 Onemore 移植：agent loop、provider、消息模型、工具基础类型；补上 Chat Completions 适配器和 schema 的数组校验 |
| `if-judge` | `Judge` trait，以及三个后端：Jev、LLM 裁判、测试桩 |
| `if-views` | 视图编译、预算控制、确定性序列化 |
| `if-policy` | 裁决策略、命运骰子、导演评分、趋势 |
| `if-lore` | 世界书激活、酒馆格式导入 |
| `if-pipeline` | 回合流程、任务定义、`IfTaskHost`、工具实现、失败兜底 |
| `if-app` | Tauri 命令与事件、密钥、设置 |

已落地：`if-domain`、`if-store`、`if-agent`、`if-judge`、`if-views`、`if-policy`、`if-app`。
未建：`if-lore`、`if-pipeline`。已落地 crate 之间的依赖是单向的
`if-domain → if-views → if-policy`，`if-judge` 只依赖 `if-domain`（`if-views` 反过来依赖
`if-judge`，因为 `CompiledView` 定义在那边）；`if-pipeline` 建成后依赖全部四者。

> **已知偏差**：酒馆格式导入目前在 `if-app/importer/`，而按上表它属于 `if-lore`。
> 当初放在 `if-app` 是因为导入要先跑通（需要 Tauri 的文件读取入口），而 `if-lore` 还没建。
> 迁移时机：等语义抽取（主体 / 事实 / 故事线）落地时——那时 `if-store` 与 `if-domain`
> 之间的映射会变成一个有类型的模块，`if-lore` 才真正有内容可装。

**世界资产写入的两层分工**（[10 §7.0](10-世界创建与导入.md)）：

- `if-store::library` 只认不透明 `payload` + 拆表的设定条目，并**保证**「按来源整组替换」；
- `if-app::library` 负责把 `ImportedWorld` 拆成那个形状，包括来源身份键与内容哈希的推导。

反过来让 `if-store` 认识 `ImportedWorld`，依赖方向就指反了（`if-store` 是底层）。

## 4. Judge 接口

```rust
pub trait Judge: Send + Sync {
    /// 一个请求 = 一个视图 + 多个问题（见 07 §2）
    fn judge(&self, request: &JudgeRequest, cancel: &AtomicBool) -> Result<JudgeResponse, JudgeError>;
    fn backend(&self) -> JudgeBackend;   // Jev { version } | Llm { model } | Stub
}

pub struct JudgeRequest {
    pub view: CompiledView,              // 已序列化的 state，加上视图元数据（种类、持有者、hash）
    pub questions: Vec<Question>,        // 模板 ID@版本 + 填充后的措辞 + 原语参数
}
```

- 同步接口，与 Onemore 的线程模型保持一致；多个视图的请求用 scoped threads 并行发出。
- 测试桩按脚本返回固定的概率，用于测试回合流程。
- **Jev 后端要点**（见 [07 §1](07-Jev问题库.md)、[14](14-Jev实测.md)）：端点是 `POST /api/alpha/decisions`，不是 chat/completions；`Question` 的原语参数要把 `choice`（record）和 `score`（有序 array）的 `criteria` 分成两个类型，不要用一个字段装两种形态；返回的概率在 `answers.<id>.noul`，Score 是 0 基连续值并附 `legend`。
- Jev 的 400 是**请求不合规**（代码缺陷），不进入重试；只有 5xx / 超时才走退避重试（[06 §9](06-裁决策略.md)）。

## 5. 线程与 IPC

- 每个打开的世界一个工作线程，持有该世界的存储连接和回合状态。
- 前端 → 核心：Tauri 命令，例如 `submit_if`、`confirm_ruling`、`continue_turn`、`observe`、`stop`、`fork`、`rewrite`、`reroll`、`rollback`、`open_world`、`create_world`、`import_card`。
- 核心 → 前端：Tauri 事件，例如 `stage_progress`、`ruling_card`、`beat_displayed`、`turn_committed`、`error`。
- 前端的状态只是当前世界线投影的缓存，权威状态始终在 Rust 端。
- `if-app` 当前已实现世界生命周期基础命令：`create_world`、`open_world`、`close_world`、`get_world_snapshot`；打开 / 创建后的状态通过 `world://opened` 通知，关闭通过 `world://closed` 通知。每次只保留一个世界工作线程，线程独占该世界的 SQLite 连接。回合命令及前端投影订阅仍待接入。
- 当前已增加 `submit_if`：在世界工作线程内串行追加一个 `if_injected` 事件并返回新投影；它是待解析 / 待裁定的落盘入口，不代表完整 IF 回合已经完成。
- `parse_if` 当前是无网络的确定性预解析器，只输出可回归的草案（导演指令标记、IF 类型启发式、时间锚点、作用范围和锁定建议）；语义忠实度、冲突与重释必须交给后续 T-parse/Jev 阶段。
- **世界库**（世界资产的持久化，[10 §2](10-世界创建与导入.md)）走的是应用级存储，不在工作线程里：
  `list_worlds` / `get_world_asset` / `delete_world_asset` / `import_world_to_library` /
  `import_world_file_to_library` / `create_written_world`，由 `AppState.library` 直接持有连接。
  理由是世界资产与会话无关——它读写的对象是「用户准备的稿子」，不是「某个世界被推进的历史」。
  写入类命令统一返回 `AssetChange { detail, assets }`：详情给预览用、列表给列表用，省一趟往返。

## 6. 存储

**两个库，两个对象**（[10 §1](10-世界创建与导入.md)）：

- 会话：每个世界一个 SQLite 文件（`.ifworld`），放在数据目录下。
  表：`events`（只追加）、`world_lines`、`turn_records`、`snapshots`、`beats`、`lore_entries`、`question_versions`。
- 世界库：应用级一个 `library.db`（与 `settings.json` 同目录）。
  表：`world_assets`、`world_sources`、`world_lore`、`world_sessions`、`library_meta`。

分开是刻意的，不是历史包袱：删会话不该动到世界稿，删世界也不该静默删掉引用它的会话
（后者由 `Library::delete_asset` 直接拒绝）。一个资产可以有多个会话，`world_sessions`
是这条引用的登记处。

`world_assets.payload` 存的是**不透明的 JSON**（当前是 `ImportedWorld` 的序列化结果），
存储层不解释它——解释它属于 `if-app::library` 的职责，反过来让存储层认识导入结果就把依赖指反了。
**例外是设定条目**：它们单独一张 `world_lore` 表，因为「重新导入同一张卡时按来源整组替换」
是存储层必须自己保证的规则，埋进不透明 payload 里就没法做。

`world_sources.source_key` 是来源**身份**，不是内容哈希；内容哈希另存一列。
理由与取舍见 [10 §7.0](10-世界创建与导入.md)。

其他应用级数据（提供商配置、问题库、标注集）同样放应用级文件，不走世界文件。

以世界文件为单位做 WebDAV 同步【后续】。

## 7. 密钥与安全

- API 密钥存入系统钥匙串（例如用 `keyring` crate），不进入 localStorage，也不写入世界文件。
- 所有网络请求都由 Rust 端发出，前端拿不到密钥明文。
- 正文按纯文本加受限的 Markdown 渲染，不渲染原始 HTML；Tauri 开启 CSP。
- 导入的角色卡里的脚本（JS、EJS、正则）一律不执行（见 [13](13-酒馆兼容.md)）。
- 项目根目录下的 `jevkey` 只用于开发：不提交到版本库，也不打包进应用。

## 8. 确定性

- 视图序列化使用固定的键顺序。
- 命运骰子使用固定的哈希算法（BLAKE3）。
- 重放只使用回合记录中的裁决，不重新询问模型。

## 9. 测试

- **回合流程测试**：Judge 测试桩 + 模拟的 provider。
- **重放测试**：同一事件序列必须得到同一个投影。
- **视图快照测试**：各视图的编译结果与期望一致，尤其要保证角色视图中不出现秘密。
- **工具 schema 测试**：非法参数永远到不了执行阶段（Onemore 已有同类测试，可以沿用）。

## 10. 可观测性

- 记录判定（[07 §5](07-Jev问题库.md)）、每个阶段的耗时和 token 用量。
- 回合记录可以导出，用于调试和回归。
