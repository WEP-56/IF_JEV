- World Info 页确认：条目通过关键词动态激活；支持主关键词、次级关键词及 AND ANY / AND ALL / NOT ANY / NOT ALL；常驻条目、插入顺序和插入位置；概率过滤；包含组与权重 / 优先级；递归激活；角色过滤；扫描深度和 token budget。World Info 是上下文注入机制，不保证模型一定在输出中使用内容。

### 0.1 两套方言必须区分

核实中的一个关键事实：**「卡片内 `character_book`」与「酒馆运行时世界书导出」用的是两套字段名**，导入器必须同时兼容。已实测确认：

| 语义 | CCv3 规范（`character_book` / `lorebook_v3`） | 酒馆运行时导出 |
|---|---|---|
| 主关键词 | `keys`（数组，必填） | `key`（数组或逗号分隔字符串） |
| 次级关键词 | `secondary_keys` | `keysecondary` |
| 插入顺序 | `insertion_order`（数字，越小越早） | `order` |
| 启用 / 停用 | `enabled`（布尔） | `disable`（布尔，语义相反） |
| 位置 | `position: "before_char" \| "after_char"` | `position: 0–6`（数字） |
| 逻辑 | `selective` + `secondary_keys` | `selectiveLogic: 0–3` |
| 正则键 | `use_regex`（V3 必填） | 由 `key` 内 `/pattern/` 写法表达 |
| 条目 id | `id` | `uid` |

`crates/if-app/src/importer/lorebook.rs` 按此表做方言判定与归一化。

### 0.2 社区分发实况：世界设定多数内嵌在卡里

2026-09-26 抽样实测（foreverse-app/character-card-skills 全部 18 张公开 V2 卡，CC BY 4.0）：

| 指标 | 实测 |
|---|---|
| 含非空 `character_book` 的卡 | **18 / 18（100%）** |
| 每条目数 | 平均 8 条（中位 8，范围 4–16） |
| 世界书字数 / 人设（描述 + 性格 + 场景）字数 | **1.60** —— 约 **62% 的世界设定写在 `character_book` 里** |
| 常驻条目 / 全部条目 | 52 / 152（34%） |
| 带关键词（条件触发）条目 | 101 / 152（66%） |
| 极端案例 | `the-lighthouse`：世界书 17165 字 vs 人设 3839 字（4.5 : 1），本质是「世界 + 一个观察者」 |

2026-09-26 又补测了两张用户提供的真实 PNG 卡（spec 3.0，见 §6.4）：148 条 / 100,526 字的武侠世界卡，
其 `description` / `personality` / `scenario` **全为空**——「卡」只是一个装世界书的壳。
这从正反两面印证了同一条结论：**卡不是角色，卡是分发容器**。

**机制原因**（SillyTavern 官方文档）：世界书可以绑定到角色（Character Lore）。
**导出角色卡时，这个文件会被自动嵌入卡内**成为 `character_book`。
所以社区里独立流传的世界书很少——不是作者不写，而是**分发格式把世界书吞进了卡里**。

三条必须计入设计的推论：

1. **独立世界书只嵌入 primary 一个**（官方原文：only the primary World Info file gets exported with the character）。
   作者在 ST 里给一张卡挂了多个世界书时，导出后其余会丢。
   → **独立世界书导入路径不能砍**，它是补回丢失部分的唯一途径。
2. **同一个世界书可被多张卡复用**（官方建议可跨角色复用一个世界书）。
   → 把第二张卡导入同一世界时会出现**大量重复条目**，导入必须做**去重 / 合并提示**。
3. **卡内 `character_book` 是「绑定那一刻的快照」**，且更新卡不会自动更新已绑定的世界书
   （ST 的更新流程是 解绑 → 重绑 → 重新导出）。
   → 重新导入同一张卡时，应按来源**整组替换**该卡带来的条目，而不是逐条追加。
   → 这要求每条条目保留 **origin**（来源类型 + 来源卡 / 文件 + 条目 uid + 卡版本），
   而不仅是当前的 `source_uid` / `source_dialect`。

## 3. 角色卡 → 世界

### 3.1 格式【已核实】

- V2：`{ spec: "chara_card_v2", spec_version: "2.0", data: {...} }`。PNG 中存放在名为 `chara` 的 **`tEXt` 块**里，块内是 JSON 字符串经 UTF-8 → base64 编码【已核实】。
- V3：`spec: "chara_card_v3"`，PNG 中存放在 **`ccv3`** 文本块里。**同时存在 `chara` 与 `ccv3` 时优先 `ccv3`**【已核实】。新增字段：`assets`、`nickname`、`creator_notes_multilingual`、`source`、`group_only_greetings`、`creation_date`、`modification_date`；其中 `group_only_greetings` 在 `data` 中**必须存在**（可为空数组）。`character_book` 在 V3 变为可选。世界书条目支持 `@@depth` 这类装饰器（以 `@@` 开头，回退装饰器用 `@@@`）。
- 独立世界书导出格式为 `{ spec: "lorebook_v3", data: Lorebook }`【已核实】。
- 角色卡条目 `position` 只允许 `before_char` / `after_char`；深度插入由装饰器 `@@depth` 表达，不是 `position` 取值【已核实】。导入器同时兼容编辑器写出的 `before_an` / `at_depth` 等扩展值。
- V3 另引入 CHARX（zip，根目录 `card.json`，资产用 `embeded://` URI）；v1 不导入 CHARX。
- `extensions`：应用私有数据。规范要求导入时保留，不得丢弃。
- 实现位置：`crates/if-app/src/importer/`（`card.rs` 角色卡、`lorebook.rs` 条目、`png.rs` PNG 文本块、`model.rs` DTO）。

## 4. 社区变量卡【待核实】

根据社区资料，常见的变量系统（例如 MagVarUpdate，也就是 MVU，配合酒馆助手和提示词模板插件使用）大致是这样工作的：

- 初始变量写在特定的世界书条目里，例如名称中带 `[InitVar]` 的条目。
- LLM 在回复中输出更新命令，例如在 `<UpdateVariable>` 块里写 `_.set('路径', 旧值, 新值);//原因`，由脚本解析后写入聊天变量（例如 `stat_data`）。
- 世界书条目可以用 EJS 模板按变量值条件化，例如 `<% if (getvar('…') > 50) { %>`。

IF 中的对应关系：

| 变量卡 | IF |
|---|---|
| 初始变量 | 命题 + 初始事实（数值 → scalar，文本 → text 或 enum） |
| 更新规则说明（通常写在世界书条目里） | 由 LLM 转成机制或触发器的候选，在世界卡中由用户确认 |
| 条件化条目 | 设定条目的 `when` 条件（[08 §5](08-视图与世界书.md)） |
| 状态栏 | IF 的右侧面板本来就有，按玩家视图显示 |

根本区别在于：**IF 不需要 LLM 输出更新命令。** 状态变化来自候选、Jev 判定和命运骰子，这正是 IF 与变量卡的分水岭。

卡中的 JS、EJS、正则等脚本一律不执行，只作为文本参考。

| 5 | 卡内嵌 `character_book` 的 `position` 只有 `before_char` / `after_char` | — | 世界 / 场景 / 文风三段**无法**从卡里推出，只能由 T-parse 或用户指定（印证 [02 §9.1](02-世界模型.md)） |
| 6 | 作者用 `comment` 当条目标题，并在内容首行自标段落 | `基础设定：世界观`（`<world_setting>`）、`武学：金刚不坏神功`、`wguide`（`objective:`）、`Core Principles`（`style_guide:`）、`background`（`character_background:`） | T-parse 有确定性线索可依；`LoreSection::Style` 有了真实样本 |
| 7 | 规模 | 卡内 148 条，**解析出 147**（1 条空内容被跳过）/ 100,526 字符，单条最长 6,033 字符；另一张 3 条 / 1,997 字符 | 上下文预算必须真做，整卡注入不可行；讨论数量时必须区分「卡里的」与「解析出的」 |
| 8 | 存在「世界书穿马甲」与「galgame 卡」两极 | 大乾卡 `description` / `personality` / `scenario` 全为空（0 字符），实体全在那 147 条设定里；风之絮言 `description` 3,479 字符 + 3 条文风条目、含 `{{user}}` | 印证「世界是主体，角色是绑定节点」：有的卡 100% 是世界，有的卡 100% 是角色。导入不能假设其中任一种形态 |
| 9 | 残留空条目 | 大乾卡第 129 条 `comment: "总结"`、`content: ""` | 跳过是对的，但必须给出 warning，不能静默少一条（已落地） |

由此修正的导入器行为：

- 条目字段按「顶层 → `extensions`」分层读取，`null` 视为未设置。
- 归段优先取 `extensions.position`（数字枚举），顶层字符串作为回退。
- `sticky` / `cooldown` / `delay` 只认正数。
- `use_regex` 提醒只在 keys 真的含正则元字符时给出（实测两张卡全标 `true`，原来的提醒是纯噪音；`风之絮言` 的 keys 里含 `(`，这条提醒才是真的）。
- 空正条目被跳过时报告条数。
- 不再臆造 `genre` 占位值（原为 `待整理`）。

由真实卡得出的另一个修正：两张卡实测 `assets = 0`、`带装饰器 = 0`——它们**没有**用到 V3 的
`assets` 与 `@@` 装饰器。所以那两个分支仍只有合成 fixture 覆盖，别因为「跑过真实 PNG 卡」
就以为 V3 分支也验过了（见 §6.3）。

### 6.5 真实卡落库实测（2026-09-26）

`examples/inspect_card` 只体检、**不落盘**，所以「PNG 字节 → 解析 → 映射 → 写进 `library.db`
→ 再读回来」这条链路在真实卡上此前是空白。现已由
`crates/if-app/tests/library_roundtrip.rs` 覆盖（样本不在则跳过，不产生假红）。

实测量级——这也是 **IPC 与 SQLite 要传的数据规模**：

| 卡 | 源文件 | 来源附件 | 条目 | 归段 |
|---|---|---|---|---|
| `南疆风云大乾风华录_武侠江湖.png` | 1886 KB | **418 KB** | **147** | Character 145 / Scene 2 |
| `风之絮言.png` | 711 KB | 25 KB | 3 | Scene 3 |

三个值得记下的事实：

1. **147 条，不是 148**。卡里确实有 148 条，其中 1 条是空内容残留（§6.4 第 9 行），
   被跳过并给出 warning。**少的那条恰好是 `position: 4` 的条目**，所以归段是
   Scene 2 而不是 §6.4 记的 3——这不是回归。凡涉及「条目数 / 归段数」的记录，
   都要区分**卡里的数**与**解析出的数**。
2. **来源附件是内嵌 JSON，不是 PNG**：1886 KB → 418 KB。存档时若误存二进制，
   世界库里会躺着几 MB 的图且无法用于重导；回归里用「附件以 `{` 开头且长度不同于源文件」钉住。
3. **重导幂等**：同一张卡连导 3 次，条目数、资产数、来源记录数都不变
   （`real_card_reimport_does_not_double_entries`）。这是世界库存在的理由，值得单独失败一次。
