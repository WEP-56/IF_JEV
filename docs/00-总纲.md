# 00 总纲

> IF 设计文档 v0.1 · 草案

## 1. 定位

IF 是一个面向反事实世界与互动叙事领域的 **AI agent harness**。它把符合行业规范的 agent runtime、工具协议、视图隔离、Jev 判断、确定性裁决、事件溯源和可重放执行组合成一套可复用的领域基础设施。

它的首个宿主应用是 **「世界书 + 绑定角色」的世界沙盒**：

- **世界是主体，角色是绑进世界的节点。** 用户导入世界书（设定、规则、地点、势力、历史）与绑定其上的角色；世界在这些材料之上**被动、客观地自我推进**。
- **它不是 LLM 驱动的 galgame。** galgame 以角色为中心——选一个角色（或多角色群聊），LLM 演他，世界只是角色的背景板。IF 反过来：**世界是主角，角色在世界里自己活**。
- **用户不在世界里。** 用户唯一的修改动作是注入 IF（权威反事实断言），其余是观测与继续。用户不扮演任何角色，也不决定角色下一步做什么——即 §3 里"用户不拥有"的那一栏。
  因此 `{{user}}` 转成**由世界推演的主角**（D14）：**你不扮演主角，你改写主角的命运。**
- **Jev 是「合理与真实」的执行者。** 没有 Jev，IF 只是一个更麻烦的酒馆。Jev 在四处约束 LLM：用户 IF 的兼容性、候选的合理性、已展示正文的合规性、回收抽取的忠实性；其中**正文合规检查**（不得违背已提交事实、不得泄露角色认知边界外的信息）是"真实感"最直接的来源，也是相对纯 LLM 写作的唯一硬通货。

因此，IF 有两个层次：

- **Harness 层（核心产品）**：负责 agent 的任务生命周期、工具调用、权限与视图、提议审查、Jev / LLM Judge、策略裁决、状态提交、审计和重放。它不依赖某一个具体 UI，也不把叙事文本当作唯一输出。
- **叙事宿主层（首个应用）**：提供世界书 / 角色卡导入、IF / 观测 / 继续三种用户动作，以及把 agent 运行结果呈现为故事的界面。它用来验证 harness 在开放世界和长回合叙事中的连续性、可干预性和安全边界。

**范围提示（2026-09-26）**：酒馆只作为**世界材料的来源**与**交互样式的参考**，不作为要对齐的生态。相关兼容范围已冻结在 [13 §1](13-酒馆兼容.md)，口径为「酒馆导入」，不承诺与 SillyTavern 行为一致。

在一次运行中：用户提供领域意图，LLM 通过工具提出结构化提议，Jev 对明确问题进行判断，确定性引擎按策略裁决并提交，LLM 再把已提交或获准展示的结果表达为故事。

技术层面：

> The user asserts. The LLM proposes. Jev judges. The engine resolves and commits. The LLM narrates.
>
> 用户断言，LLM 提出，Jev 判断，引擎裁决并提交，LLM 叙述。

早期构想里"Jev 作出裁定"是一步；本设计把它拆成两步：Jev 只输出分布，称为**判定**；引擎依据明确的策略把分布变成结果，称为**裁决**。随机性因此是机械的，可审计，也可重放。

## 2. Harness 的职责边界

IF harness 不是“让模型自由写故事”的封装，也不是一个把 Jev 接到聊天界面的适配器。它必须掌握以下控制面：

1. 为每类领域任务编译可见视图和工具集合。
2. 校验并收集 agent 提议，在提交前交给 Judge 和策略层审查。
3. 将通过的效果写入工作区，再由事件日志原子提交。
4. 记录模型、问题、判定、裁决、工具调用和版本，使运行可审计、可重放、可测试。
5. 允许替换宿主 UI、LLM provider、Judge 后端和领域工具，而不改变核心 runtime 合同。

## 3. 四方权力

| 参与方 | 拥有 | 不拥有 |
|---|---|---|
| 用户 | 现实修改权（IF）、观测权、推进权（继续）、世界线操作权 | 决定角色下一步行动、谁如何得知、后果、叙事焦点、节奏、时间推进、结局 |
| LLM | 语义创造与表达权：解析、候选、计划、正文、抽取 | 提交状态、覆盖 Canon、决定关键结果、宣布结束、绕过 Jev |
| Jev | 判定权：对明确的问题输出概率、分布或评分 | 生成内容、保存状态、直接执行决定 |
| 引擎 | 事实存储权、规则执行权、裁决权 | 语义理解（一律委托 LLM 或 Jev） |

## 4. 核心原则

| 编号 | 原则 | 内容 |
|---|---|---|
| P1 | 最小承诺 | IF 只建立使其成立所必需的最小事实，不自动承诺任何次生后果。 |
| P2 | 事实与认知分离 | 世界中为真（Reality）、主体相信为真（Belief）、主体声称为真（Claim）是三类独立记录。 |
| P3 | 候选裁定 | LLM 生成候选，Jev 返回分布，引擎依据明确策略裁决。LLM 的任何产出，在进入正式状态或展示给玩家之前，都要经过 Jev 审查。 |
| P4 | 状态闭环 | 正文展示后必须做事实回收；已展示的承重事实必须进入事件日志。 |
| P5 | 展示边界 | 正文展示前，Jev 可以否决；展示后，Jev 只能解释和校对，不能否决。 |
| P6 | 事件溯源 | 事件日志是唯一真相；状态、认知、关系、故事线都是投影。每一项提交都能追溯到"事件 → 候选 → 判定 → 裁决"。 |
| P7 | 语义定策略 | 用阈值、抽样还是加权，由问题的语义类别决定，而不是由它属于哪个领域决定。 |
| P8 | 命运骰子 | 随机数由世界种子和稳定的决策键派生；同一决策在不同世界线上用同一颗骰子。重放直接使用已记录的裁决。 |
| P9 | 视角隔离 | 每个消费方（LLM 和 Jev 都算）只接收它有资格看到的视图。判断角色行为时，不能让判定者看到角色不知道的事实。 |
| P10 | 双重时间 | 世界发生时间与叙述呈现顺序分别记录。 |
| P11 | 分辨率 | 当前镜头高分辨率模拟，相关后台批量结算，无关世界只维护宏观趋势。 |
| P12 | 导演分权 | 引擎管理节奏结构与硬约束，Jev 提供语义判断，LLM 提供候选与叙事表达。 |
| P13 | IF 唯一入口 | 用户对世界的一切修改，包括在界面上直接编辑角色或世界，都要经过 IF 流程和裁定卡。 |
| P14 | 可替换裁判 | 所有判定通过统一的 Judge 接口执行；Jev、LLM 裁判、测试桩都可以作为后端。 |

来源：P1–P4、P6、P7、P10–P12、P14 来自首轮产品评审（P7 原名"确定性边界"，这里细化为按问题语义划分）；P5、P8、P9、P13 为后续评审补充。

## 6. 禁止的定位错误

1. **把 Jev 当成另一个 LLM。** 让 Jev 自由构思"接下来发生什么"，它的优势就没了。Jev 只在有限候选上做判断。
2. **让 LLM 直接维护状态。** LLM 只能提出状态，否则同义字段、事实漂移、记忆遗漏会不断累积。
3. **把用户当导演。** 用户只能断言事实，不能要求"让角色表白""切换到十年后""让反派失败"。
4. **让 Jev 成为数据库。** Jev 的输出是判定；最终的事实、状态、事件、时间线由引擎保存。
5. **把"符合程度"当成"发生概率"去掷骰。** 只有发生类问题的概率才能拿去抽样（见 [06](06-裁决策略.md)）。
6. **让判定者或写作者越过视角。** 包括把角色不知道的秘密放进判断角色行为的请求里。
7. **展示之后再否决正文。** 否决只能发生在展示之前。

## 7. 研究命题

能否通过事件溯源、认知隔离和概率化的戏剧管理，让生成式长篇叙事同时保持开放性、连续性与可干预性。

## 8. 第一版不可推迟项

首轮产品评审确认：

1. 最小承诺原则
2. Reality / Belief / Claim 分层
3. 正文后的状态回收

评审补充（已确认）：

4. 事件日志从第一天起就作为存储结构（世界线重算可以以后再做）。
5. 问题库带版本号，并为关键的约束类问题准备一小套人工标注样本。

缺少前三项，故事运行十几轮后，"玩家读到的世界"和"引擎认为的世界"就会分裂。缺少后两项，以后补救的代价会非常高。
