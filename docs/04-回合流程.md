# 04 回合流程

本文描述一轮的阶段划分。涉及 LLM 的阶段都以 **agent 任务**的形式运行；任务内部如何由 Jev 主导，见 [05](05-Agent运行时.md)。

## 1. 回合类型

| 类型 | 触发 | 说明 |
|---|---|---|
| IF 回合 | 用户提交 IF | 完整流程 |
| 继续回合 | 用户点"继续" | 跳过解析与锁定，由角色目标与趋势驱动 |
| 观测 | 用户发起观测 | 不产生场景，只更新玩家认知 |
| 后台结算 | 场景结束后按需触发 | 不展示，见 [09](09-世界模拟.md) |
| 世界创建 | 新建世界 | 见 [10](10-世界创建与导入.md) |

## 2. IF 回合

| # | 阶段 | 执行 | 产出 | 检查 |
|---|---|---|---|---|
| 1 | 指令检测 | Jev | 输入是否为导演指令 | `q.input.is_directive` |
| 1a | 指令改写 | 任务 T-rewrite | 1–3 条 IF 形式的改写 | `q.input.is_directive`、`q.input.rewrite_preserves` |
| 2 | 解析 | 任务 T-parse | IF 草案 | `q.if.parse_faithful`、`q.if.type` |
| 3 | 预检 | 引擎 + Jev；有冲突时加任务 T-reconcile | 冲突与重释方案、世界线偏移 | `q.if.contradicts_displayed`、`q.if.compatible_with`、`q.if.reconcile_plausible`、`q.if.prior_plausibility` |
| 4 | 裁定卡 | 用户 | 确认、修改或取消 | — |
| 5 | 锁定 | 引擎 | `if_injected`、锁定的事实、规则编译结果；回溯型按 [03 §7](03-事件与世界线.md) 执行 | — |
| 6 | 影响候选 | 任务 T-impact | 候选（含依赖关系、互斥组） | `q.cand.relevance`、`q.cand.in_character`、`q.cand.knowledge_gap` |
| 7 | 分层裁决 | 引擎 + Jev | 预演状态（Proposed） | 发生类问题 + 命运骰子，见 [06 §4](06-裁决策略.md) |
| 8 | 场景候选 | 任务 T-scenes | K 个场景候选【初始值 K = 4】 | `q.scene.resolves_thread`（受保护的线直接否决） |
| 9 | 导演选择 | 引擎 + Jev | 选中的场景；未选中的记为"未选之路" | 导演评分，见 [06 §6](06-裁决策略.md) |
| 10 | 场景计划 | 任务 T-plan | Scene Plan | 计划检查（复用节拍检查的模板） |
| 11 | 节拍渲染 | 任务 T-render（正文走文本输出，用分隔标记切分节拍，见 [05 §7](05-Agent运行时.md)） | 逐个放行的节拍 | 全套节拍检查，见 §4 |
| 12 | 回收 | 任务 T-extract（玩家阅读时在后台运行） | Observed 的事实、声称、新主体 | `q.extract.*` |
| 13 | 提交 | 引擎 + Jev | 对账后的事件；故事线、趋势、时间、机制的更新 | `q.thread.stage`、`q.tendency.push` |
| 14 | 后续 | 引擎，加任务 T-offscreen、T-inspire | 后台结算、预生成、命运节点提示、IF 灵感 | `q.window.fate_node` |

### 2.1 引擎注入的硬约束（第 10 步）

场景计划由 LLM 展开，但下面这些约束由引擎直接写入，不由 LLM 决定：

- 受保护故事线的 forbidden_resolutions。
- 在场角色的认知边界（谁知道什么）。
- 当前生效规则的语义约束。
- reveal_allowed 以外的秘密清单。这份清单只进入检查视图，不进入叙事视图。

### 2.2 投机执行

- 裁定卡展示期间，预先跑第 6 步。如果用户修改了裁定卡，丢弃结果。
- 玩家阅读期间，为"继续"预先跑第 8 步。用户直接点"继续"时，可以立刻进入第 9 步。

## 3. 继续回合

第 6 步换成任务 T-drive：根据角色的目标与意图、接近阈值的趋势、机制触发器，提出角色自驱的候选。之后同 IF 回合的第 7–14 步。

如果没有任何候选，导演可以选择一个时间跳跃场景：推进世界时间，执行机制和后台结算。

## 4. 节拍放行（第 11 步）

1. T-render 在一次模型调用里连续输出正文，用分隔标记切分节拍（[05 §7](05-Agent运行时.md)）。host 每收满一个节拍就送检一次。
2. 引擎用检查视图，把以下问题合并成一个请求：
   - `q.beat.violates_fact`（每条相关的锁定事实）
   - `q.beat.violates_rule`（每条相关规则）
   - `q.beat.knowledge_leak`（`ScenePlan.present` 中的每个在场角色）
   - `q.beat.forbidden_resolution`（每条禁止项）
   - `q.beat.reveals_secret`（每个未批准揭示的秘密）
   - `q.beat.stop_reached`
   - `q.beat.goal_done`
3. 全部通过：展示节拍，立即写入 `beat_displayed`。如果停止条件已经达成，结束场景。
4. 有未通过的：节拍不展示、不进入历史；host 把有针对性的修改说明追加进对话，让模型重写这一段。
5. 同一节拍最多重试 2 次【初始值】。超过后依次兜底：
   1. 如果不是必需的节拍，跳过它；
   2. 降低温度、附上完整约束清单，保守地重写一次；
   3. 在最后一个已展示的节拍处结束场景。
6. 每个场景最多 6 个节拍【初始值】；达到上限时强制结束场景。
7. **背压**：未裁决的节拍缓冲超过上限【初始值 2】时暂停读取模型输出，避免它跑在检查前面。用户点"停止"时中止调用，缓冲中未裁决的节拍一律丢弃。

## 5. 观测

1. 用户选择观测目标。
2. 引擎按可见性规则选出可以返回的信息：证据、表层信念、模糊压力。
3. 任务 T-observe 负责措辞。
4. 用 `q.observe.leaks_secret` 检查是否泄密。
5. 展示结果，写入 `user_observed`。

## 6. 并发与中断

- 渲染中点"停止"：中止当前的模型调用；已展示的节拍保留；场景在最后一个已展示的节拍处结束，照常回收和提交。
- 回收和提交完成之前，新的用户动作排队等待。
- 同一个世界同时只运行一个回合。后台结算和预生成可以并行，但必须基于已提交的投影版本，提交前检查版本（乐观锁）。

## 7. 延迟预算【实测后修订】

IF 回合在关键路径上的模型任务依次是：T-parse → T-impact → T-scenes → T-plan → T-render（第一个节拍）。T-extract 不在关键路径上。

Jev 判定延迟极低、花费极少（已确认），瓶颈在 LLM。优化手段：

- 投机执行（§2.2）。
- 稳定前缀加 prompt cache（见 [08](08-视图与世界书.md)）。
- 并行工具调用：一次提出多条候选。
- 结构类任务和叙事任务使用不同的模型（见 [12](12-工程架构.md)）。
